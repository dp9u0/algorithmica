在直接进入编译器优化（本章大部分内容的主题）之前，先简要回顾一下"全局图景"。略过枯燥的部分，把 C 程序变成可执行文件有 4 个阶段：

1. **预处理**（preprocessing）展开宏、从头文件拉取被包含的源码、剥离源代码中的注释：`gcc -E source.c`（把预处理后的源码输出到 stdout）
2. **编译**（compiling）解析源代码、检查语法错误、将其转换为中间表示、执行优化，最后翻译成汇编语言：`gcc -S file.c`（生成 `.s` 文件）
3. **汇编**（assembly）把汇编语言变成机器码，只是 `printf` 这类外部函数调用会被替换成占位符：`gcc -c file.c`（生成 `.o` 文件，称为*目标文件*（object file））
4. **链接**（linking）最终把函数调用的实际地址填进去完成解析，产出可执行的二进制文件：`gcc -o binary file.c`

每个阶段都有改进程序性能的机会。

### 过程间优化

之所以有[链接](../stages)这最后一个阶段，是因为逐个文件地编译程序、再把它们链接到一起，既更容易也更快——这样既能并行编译，也能缓存中间结果。

它还让以*库*的形式分发代码成为可能，库分静态和共享两种：

- *静态*库就是一组预编译好的目标文件的集合，编译器把它们与其他源码合并，生成单一可执行文件——就像平常的编译一样。
- *动态*库或*共享*库是预编译好的可执行体，带有额外的元信息，说明它的可调用对象在哪里，对这些对象的引用在运行时解析。顾名思义，这允许在多个程序之间*共享*同一份编译产物。

使用静态库的主要优势在于可以执行各种*过程间优化*（interprocedural optimization）——它们需要的上下文不止是库函数的签名，比如[函数内联](/hpc/architecture/functions)或死代码消除。想强制链接器只查找并只接受静态库，可以传 `-static` 选项。

这个过程叫*链接时优化*（link-time optimization，LTO）。它之所以可行，是因为现代编译器还会在目标文件里存储某种形式的*中间表示*（intermediate representation），从而能对整个程序做一些轻量级优化。这也让在同一个程序里混用不同的编译型语言成为可能——只要各语言的编译器使用同一种中间表示，甚至可以跨语言边界优化。

LTO 是个比较新的特性（GCC 大约 2014 年才有），而且远不完美。在 C 和 C++ 里，要确保分离式编译不损失性能，办法是创建*仅头文件库*（header-only library）。顾名思义，它就是包含所有函数完整定义的头文件集合，只要 include 它们，编译器就能用上所有可能的优化。代价是每次都得从头重新编译库代码，但这种方式保有完全的控制，确保性能毫无损失。

### 检查输出

检查各个阶段的输出，能让你对程序里发生的事获得有用的洞见。

给编译器传 `-S` 标志就能从源码得到汇编，它会生成一份人类可读的 `*.s` 文件。如果再传 `-fverbose-asm`，文件里还会有编译器的注释，标明源代码行号和一些所用变量的信息。如果只是个小片段而你又犯懒，可以用 [Compiler Explorer](https://godbolt.org/)——一个非常顺手的在线工具，能把源代码转成汇编、按颜色高亮逻辑汇编块、附带一份小型 x86 指令集参考，还提供大量其他编译器、目标平台和语言可选。

除汇编外，另一个最有帮助的抽象层级是编译器执行优化所基于的中间表示（IR）。IR 定义的是计算本身的流程，对寄存器数量、具体指令集这类体系结构特性的依赖小得多。查看 IR 常常有助于理解编译器是*怎么看待*你的程序的，不过这稍微超出了本书的范围。

本章主要使用 [GCC](https://gcc.gnu.org/)，必要时也会为 [Clang](https://clang.llvm.org/) 复现示例。两款编译器大体上相互兼容，多数情况下只在一些优化标志和细微的语法细节上有差别。
