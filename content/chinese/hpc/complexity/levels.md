为什么 Google 这样的公司要在面试里让人在白板上解算法题？

原因在于，工程师超过 10000 人的组织与外面的世界非常不同。

当然，随着职业生涯的推进，这些编码题会被复杂的系统设计问题和管理能力评估取代。只是这暂时与你无关，因为你不可能一出校门就坐上高级职位。

这一节主要只是我关于性能工程职业路径的一些闲话。

大部分计算机科学知识都被高层语言和库抽象掉了

我假设你要么想去工业界工作，要么想留在学术界、同时做点真正有用的事。

算法设计是一种你只在 20% 的时间里用到、却贡献了 80% 成功的技能。

确实有一些领域，性能在其中是杀手级特性。但看看 Java 生态：它慢得要命，却仍然驱动着大数据生态的绝大部分，运行着大多数 Android 应用。Java 和其他基于 VM 的语言（比如 WebAssembly）短期内不会消失。

当然，招聘里也存在大量~~愚蠢~~偏见。有的大公司完全不问这些，也有的公司全员由退役或现役算法竞赛选手组成。这说得通：如果人们相信某种技能被低估了，那为什么还要雇有这种技能的人呢，反之亦然。

无论如何，大 O 记号并不是公司真正想要的东西。重点不在于写出最优的问题——更在于避开那些慢得可怕的：那些不能随规模扩展的。算力的确在持续变便宜。

如果你有过算法竞赛经历，会尤其沮丧：你不会去解这类问题，哪怕面试里真的问了。要解决它们，你需要的是另一类资历。渐进最优的算法已经存在，你要优化的是常数因子。不幸的是，只有寥寥几所大学教这个。

## 优化的层次 {#the-levels-of-optimization}

按软件优化的能力，程序员可以分成几个"层次"：

0. *新手*。完全不考虑性能的人。他们通常写高层语言，有时写声明式/函数式语言。大多数"程序员"停留在此（这没什么不好）。
1. *本科生*。了解大 O 记号、熟悉基本数据结构和各种套路的人。LeetCode 和 CodeForces 选手都在这一层。这也是进大公司的门槛——它们有大量内部软件、超大的规模，而且找的是能长期干的人，所以才会问编程语言这类东西。
2. *研究生*。知道并非所有操作生而平等；了解其他代价模型，比如外部存储器模型（external memory model，B-tree、外部排序）、字模型（bitset）或并行计算，但仍停留在理论层面。
3. *职业开发者*。知道这些操作真实耗时的人。清楚分支预测失败的代价高昂、内存按缓存行划分。会一些基本的 SIMD 技巧。
4. *性能工程师*。确切知道硬件内部正在发生什么。分得清延迟与带宽，知道执行端口。懂得有效使用 SIMD 和指令集的其余部分。能读汇编、会用剖析器。
5. *Intel 员工*。掌握微架构特定的细节。这已超出普通工程师的职责范围。

在本书中，我们假设普通读者大约处在第 1 层，并希望读到结尾时能到达第 4 层。

设计算法时你也应该沿着这些层次走一遍。首先让它先能跑起来，然后选一批渐进复杂度还算最优的算法。接着考虑它们在内存操作或并行执行能力上的表现（哪怕你考虑的是单线程程序，一个核内部仍然会有大量并行性，所以这个模型极其），然后再走向具体实现。正如 Knuth 曾经说过的，避免过早优化。

对大多数 Web 服务来说，效率不重要，但*延迟*重要。

如今靠的已不是提升效率。

一次页面浏览通常产生大约 0.1 到 1 美分的收益。这是把用户注意力变现的典型费率。比方说，如果我直接装上 AdSense，大概就是这个水平——具体取决于我的读者主要来自哪里、他们有多少人在用广告拦截器。

与此同时，一台独占一个核加 1GB 内存的服务器（对一个简单的 Web 服务来说，这是荒谬地多的资源）摊算下来每秒成本约为一美分的百万分之一。这点钱够你取回 100 张照片。

Amazon 做过一个实验，用人工注入的延迟对他们的服务做 A/B 测试，发现 100ms 的延迟会减少收入。大多数其他服务也是如此，比如在 Twitter 上你的"心流"一断，用户很可能就开始想别的然后离开。如果 Google 的延迟超过几秒，人们只会觉得 Google 坏了，然后走人。

延迟的最小化通常可以靠并行计算完成，这也正是分布式系统更多在可扩展性上下功夫的原因。本书这一部分关心的是提升算法的*效率*，延迟降低只是它的副产品。

不过，仍有一些用例要在质量与服务器成本之间做权衡。

- 搜索是分层的。通常有很多层更准但更慢的模型。每一层参与排序的文档越多，最终质量越好。
- 游戏。规模越大越好玩，但算力需求也随之增长。这也包括 AI。
- AI 工作负载——那些拥有海量数据的，比如语言模型。模型越重需要的算力越多。它们的瓶颈不在数据量，而在效率。

本质串行的算法，或资源受限的场合。在大 PDF 里 Ctrl+F 是痛苦的。因数分解。

## 估计影响 {#estimating-the-impact}

有时优化需要发生在调用方那一层。

SIMDJSON 加速了 JSON 解析，但也许一开始就不用 JSON 才更好。

Protobuf 或扁平的二进制格式。

还有一个鸡生蛋、蛋生鸡的问题：一种方法因为慢、不可行，所以没多少人用。

实现成本、bug、可维护性。世界上大多数软件效率低下，这完全没问题。

成为更好的程序员意味着什么？更快的程序？更快的工作速度？更少的 bug？是这些的组合。

实现编译器优化或数据库是高杠杆活动的例子，因为它们相当于对其他一切征的税——这也正是为什么你看到大多数人写书专论这些特定主题，而不是泛泛的软件优化。
