浮点算术的用户完全配得上那种 IQ 钟形曲线梗图——因为它与大多数人之间的关系通常是这样发展的：

- 初级程序员到处使用它，仿佛它是一种魔法般的无限精度数据类型。
- 然后他们发现 `0.1 + 0.2 != 0.3` 或诸如此类的怪事，吓坏了，开始以为每一步计算都会被加上某个随机误差项，此后很多年都完全回避任何实数类型。
- 最后他们终于鼓起勇气，读了一遍 IEEE-754 浮点数的工作规范，开始恰当地使用它。

不幸的是，太多人还停留在第二阶段，滋生出关于浮点算术的种种误解——认为它本质上学不精确、不稳定，还比整数算术慢。

![](/en/hpc/arithmetic/img/iq.svg)

但这些统统是迷思。因为有了专门的指令，浮点算术常常比整数算术*更快*；而实数表示法经过彻底的标准化，在舍入方面遵循简单且确定性的规则，让你能够可靠地管理计算误差。

它可靠到什么程度呢？一些高级编程语言——最著名的是 JavaScript——干脆没有整数。JavaScript 里只有一种 `number` 类型，内部存储为 64 位 `double`，而由于浮点算术的工作方式，$-2^{53}$ 到 $2^{53}$ 之间的所有整数以及涉及它们的计算结果都可以被精确存储，所以从程序员的角度看，单独搞一个整数类型没什么实际必要。

一个显著的例外是当你需要对数字执行按位操作时——*浮点单元*（负责浮点数运算的协处理器）通常不支持这些操作。这种情况下需要把它们转换为整数，而这在启用 JavaScript 的浏览器中用得如此频繁，以至于 Arm [专门添加了一条 "FJCVTZS" 指令](https://community.arm.com/developer/ip-products/processors/b/processors-ip-blog/posts/armv8-a-architecture-2016-additions)，全称 "Floating-point Javascript Convert to Signed fixed-point, rounding toward Zero"（浮点 JavaScript 转有符号定点数，向零舍入），名字说的是什么它就做什么——用与 JavaScript 完全相同的方式把实数转成整数——这是软硬件反馈回路发挥作用的一个有趣例子。

但除非你是一个完全用实数类型来模拟整数算术的 JavaScript 开发者，你需要的多半是一份关于浮点算术的更深入指南，所以我们将从一个更宽泛的主题讲起。

## 实数表示法 {#real-number-representations}

如果需要处理实（非整数）数，你有若干种适用场景各异的选项。在直接跳到浮点数（本文的主体）之前，我们想先讨论一下现有的替代方案及其背后的动机——毕竟，回避浮点算术的人确实有他们的道理。

### 符号表达式 {#symbolic-expressions}

第一种也是最笨重的办法，是不存储计算结果本身，而是存储产生这些结果的代数表达式。

来看一个简单的例子。在某些应用（比如计算几何）中，除了加、减、乘，你还需要做不带回舍入的除法，产生一个有理数，而它可以用两个整数之比精确表示：

```c++
struct r {
    int x, y;
};

r operator+(r a, r b) { return {a.x * b.y + a.y * b.x, a.y * b.y}; }
r operator*(r a, r b) { return {a.x * b.x, a.y * b.y}; }
r operator/(r a, r b) { return {a.x * b.x, a.y * b.y}; }
bool operator<(r a, r b) { return a.x * b.y < b.x * a.y; }
// ...and so on, you get the idea
```

这个比值可以化成不可约形式，这甚至能让表示唯一：

```c++
struct r {
    int x, y;
    r(int x, int y) : x(x), y(y) {
        if (y < 0)
            x = -x, y = -y;
        int g = gcd(x, y);
        x /= g;
        y /= g;
    }
};
```

*计算机代数*系统（如 WolframAlpha 和 SageMath）就是这样工作的：它们完全在符号表达式上运算，避免把任何东西求值成实数值。

用这种方法你可以获得绝对精度，而且在范围有限（比如只支持有理数）时效果很好。但代价是巨大的计算成本，因为一般而言，你得设法保存通往结果的完整运算历史，并在每次执行新运算时把它考虑进去——随着历史增长，这很快变得不可行。

### 定点数 {#fixed-point-numbers}

另一种办法是继续用整数，但把它们当作乘以了一个固定常数来对待。本质上，这相当于把计量单位换成分度更合适的单位。

由于某些值无法精确表示，这会让计算变得不精确：你需要把结果舍入到最近的可表示值。

这种做法常用于金融软件，因为在那里你*确实*需要一种直截了当的方式来管理舍入误差，让最终的数字能对得上账。例如，NASDAQ 在其股票行情中以 $\frac{1}{10000}$ 美元为基本单位，也就是说所有交易都精确到小数点后 4 位。

```c++
struct money {
    uint v; // 1/10000th of a dollar
};

std::string to_string(money) {
    return std::format("${0}.{1:04d}", v / 10000, v % 10000);
}

money operator*(money x, money y) { return {x.v * y.v / 10000}; }
```

除了引入舍入误差，一个更大的问题是：一旦比例常数放错了位置，它们就废了。如果你处理的数字太大，内部整数值就会溢出；如果数字太小，它们就会被直接舍入到零。有意思的是，前一种情况曾在 NASDAQ [真的出过事](https://www.wsj.com/articles/berkshire-hathaways-stock-price-is-too-much-for-computers-11620168548)：伯克希尔·哈撒韦的股价逼近 $\frac{2^{32} - 1}{10000}$ = = 429,496.7295 美元时，就再也装不进无符号 32 位整数了。

这个问题使得定点算术从根本上不适合那些需要同时使用很小和很大的数字的应用，比如求值某些物理方程：

$$
E = m c^2
$$

在这个著名方程里，$m$ 通常与质子质量（$1.67 \cdot 10^{-27}$ kg）同一量级，而 $c$ 是光速（$3 \cdot 10^9$ m/s）。

> **译者注**：光速约为 3×10⁸ m/s，原文的 3×10⁹ m/s 疑为数量级笔误（不影响本节"定点数难以同时容纳大小悬殊的量"这一论点）。

### 浮点数 {#floating-point-numbers}

在大多数数值应用中，我们主要关心的是相对误差。我们希望计算结果与真值的偏差不超过比如 $0.01\\%$，而并不太在乎这 $0.01\\%$ 折算成绝对单位是多少。

浮点数通过存储若干位最高有效数字和数字的数量级来解决这一问题。更准确地说，它们用一个整数（称为*有效数字*（significand）或*尾数*（mantissa））表示，并用某个固定基数的指数来缩放——最常见的是 2 或 10。例如：

$$
1.2345 =
\underbrace{12345}_\text{mantissa}
\times {\underbrace{10}_\text{base}\!\!\!\!}
      ^{\overbrace{-4}^\text{exponent}}
$$

计算机操作的是固定长度的二进制字，所以为硬件设计浮点格式时，你会想要一种定长的二进制格式：一部分位分给尾数（换精度），一部分位分给指数（换范围）。

下面这个手工实现的浮点数希望能传达这个思想：

```cpp
// DIY floating-point number
struct fp {
    int m; // mantissa
    int e; // exponent
};
```

这样我们就能表示形如 $\pm \\; m \times 2^e$ 的数字，其中 $m$ 和 $e$ 都是有界的*且可能为负*的整数——分别对应负数或很小的数。这些数的分布非常不均匀：$[0, 1)$ 区间里的数大约和 $[1, +\infty)$ 区间里的数一样多。

注意，某些数字的表示并不唯一。例如，数字 $1$ 可以表示为

$$
1 \times 2^0 = 2 \times 2^{-1} = 256 \times 2^{-8}
$$

以及其他 28 种不会使尾数溢出的方式。

这对某些应用（比如比较或哈希）来说是个问题。为了解决它，我们可以按某种约定把这些表示*规格化*（normalize）。在十进制中，[标准形式](https://en.wikipedia.org/wiki/Scientific_notation)是总把小数点放在第一位数字之后（`6.022e23`），二进制也可以如法炮制：

$$
42 = 10101_2 = 1.0101_2 \times 2^5
$$

注意，按照这条规则，第一位总是 1。显式存储它是多余的，所以我们干脆假装它在那儿，只存储其余的位——它们对应 $[0, 1)$ 区间里的某个有理数。现在，可表示数字的集合大致是

$$
\{ \pm \; (1 + m) \cdot 2^e \; | \; m = \frac{x}{2^{32}}, \; x \in [0, 2^{32}) \}
$$

既然 $m$ 现在是非负值，我们干脆把它设为无符号整数，另外加一个单独的布尔字段表示数字的符号：

```cpp
struct fp {
    bool s;     // sign: "0" for "+", "1" for "-" 
    unsigned m; // mantissa
    int e;      // exponent
};
```

现在，让我们试着用手工浮点数实现某个算术运算——比如乘法。用新公式，结果应该是：

$$
\begin{aligned}
c  &= a \cdot b
\\ &= (s_a \cdot (1 + m_a) \cdot 2^{e_a}) \cdot (s_b \cdot (1 + m_b) \cdot 2^{e_b})
\\ &= s_a \cdot s_b \cdot (1 + m_a) \cdot (1 + m_b) \cdot 2^{e_a} \cdot 2^{e_b} 
\\ &= \underbrace{s_a \cdot s_b}_{s_c} \cdot (1 + \underbrace{m_a + m_b + m_a \cdot m_b}_{m_c}) \cdot 2^{\overbrace{e_a + e_b}^{e_c}}
\end{aligned}
$$

现在各部分的计算似乎都很直截了当，但有两个细节：

- 新的尾数现在落在 $[0, 3)$ 区间。我们需要检查它是否大于 $1$ 并规格化表示，套用公式：$1 + m = (1 + 1) + (m - 1) = (1 + \frac{m - 1}{2}) \cdot 2$。
- 由于精度不足，结果的数字很可能是（而且极有可能是）无法精确表示的。处理 $m_a \cdot m_b$ 项需要两倍的位数，我们所能做的最多就是把它舍入到最近的可表示数字。

由于需要一些额外的位来正确处理尾数溢出问题，我们从 $m$ 中预留出一位，把它限制在 $[0,2^{31})$ 范围内。

```c++
fp operator*(fp a, fp b) {
    fp c;
    c.s = a.s ^ b.s;
    c.e = a.e + b.e;
    
    uint64_t x = a.m, y = b.m; // casting to wider types
    uint64_t m = (x << 31) + (y << 31) + x * y; // 62- or 63-bit intermediate result
    if (m & (1<<62)) { // checking for overflow
        m -= (1<<62); // m -= 1;
        m >>= 1;
        c.e++;
    }
    m += (1<<30); // "rounding" by adding 0.5 to a value that will be floored next
    c.m = m >> 31;
    
    return c;
}
```

许多需要更高精度等级的应用以类似方式使用软件浮点算术。当然，你不会希望每次想乘两个实数时都执行这段代码编译出的那 10 来条指令，所以在现代 CPU 上，浮点算术由硬件实现——由于其复杂性，通常作为单独的协处理器存在。

x86 的*浮点单元*（常称为 x87）有独立的寄存器和自己的小型指令集，支持内存操作、基本算术、三角函数，以及一些常见运算如对数、指数和平方根。要让这些运算正确协同工作，浮点数表示法的另一些细节需要澄清——我们将在[下一节](../ieee-754)完成这件事。
