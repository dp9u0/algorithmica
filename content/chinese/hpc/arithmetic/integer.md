如果你在按顺序从头阅读本章，你可能会纳闷：为什么我把整数算术放在浮点算术之后讲？它不是应该更简单吗？

没错：朴素的整数表示确实更简单。但反直觉的是，正是这种简单让运算有更多机会用其他运算来表达。浮点表示笨重到其大部分运算都由硬件实现，而高效地操作整数反而需要对指令集更有创造性的运用。

## 二进制格式 {#binary-formats}

*无符号整数*（unsigned integer）就是写成二进制的自然数：

$$
\begin{aligned}
   5_{10}   &= 101_2 = 4 + 1
\\ 42_{10}  &= 101010_2 = 32 + 8 + 2
\\ 256_{10} &= 100000000_2 = 2^8
\end{aligned}
$$

当运算结果超出字长（比如对 32 位无符号整数达到 $2^{32}$ 或更大）时，它就*溢出*（overflow）了——只保留结果的最低 32 位。类似地，如果结果是负值，它就*下溢*（underflow）——把它加到 $2^{32}$ 上，使结果始终落在 $[0, 2^{32})$ 范围内。

这等价于对 2 的幂取模执行所有运算：

$$
\begin{aligned}
    256                 &\equiv 0 \pmod {2^8}
\\  2021                &\equiv 229 \pmod {2^8}
\\  -42 \equiv 256 - 42 &\equiv 214 \pmod {2^8}
\end{aligned}
$$

无论哪种情况，都会升起一个可供检查的特殊标志，但通常人们显式使用无符号整数时，图的就是这个行为。

### 有符号整数 {#signed-integers}

*有符号整数*（signed integer）通过把最高位专门用作符号位来支持存储负值，这与浮点数的做法类似。它把可表示非负数的范围砍半：32 位整数的最大值现在是 $(2^{31}-1)$ 而不是 $(2^{32}-1)$。但负值的编码方式与浮点数不太一样。

计算机工程师比程序员还懒——这不仅是出于追求简便的天性，还为了节省晶体管空间。办法就是复用你已有的其他运算的电路，设计有符号整数格式时瞄准的正是这个：

- 对 $n$ 位有符号整数类型，$[0, 2^{n-1})$ 范围内所有数的编码与它们的无符号二进制表示保持一致。
- $[-2^{n-1}, 0)$ 范围内的所有数紧接着"正"区间顺序编码——也就是说，从 $(-2^{n - 1})$（编码为 $(2^{n-1})$）开始，到 $(-1)$（编码为 $(2^n - 1)$）结束。

一种理解方式是：所有负数都被编码成从 $2^n$ 中减去它的结果——这个运算称为*二进制补码*（two's complement，补码）：

$$
\begin{aligned}
-x &= 2^{32} - x
\\ &= \bar{x} + 1
\end{aligned}
$$

这里 $\bar{x}$ 表示按位取反，也可以看作把 $x$ 从 $(2^n - 1)$ 中减掉。

作为练习，这里列举一些关于有符号整数的事实：

- 所有正数和零保持其二进制记数不变。
- 所有负数的最高位都是 1。
- 负数比正数多（恰好多一个——因为零占了一个坑）。
- 对 `int`，如果你把 $1$ 加到 $(2^{31}-1)$ 上，结果是 $-2^{31}$，表示为 `10000000`（为讲解方便，我们只写 8 位而不是 32 位）。
- 知道正数 `x` 的二进制记数，就可以用 `~x + 1` 得到 `-x` 的二进制记数。
- `-1` 表示为 `~1 + 1 = 11111110 + 00000001 = 11111111`。
- `-42` 表示为 `~42 + 1 = 11010101 + 00000001 = 11010110`。
- 数 `-1 = 11111111` 的下一个数是 `0 = -1 + 1 = 11111111 + 00000001 = 00000000`。

这种编码的主要优点是：把无符号整数转成有符号整数你什么都不用做（顶多检查一下溢出），而且大多数运算可以复用同一套电路，比较之类的情况可能只需翻转符号位。

话虽如此，你得小心有符号整数溢出。尽管它们的溢出方式几乎总是与无符号整数相同，编程语言通常把溢出的可能性视为未定义行为。如果你需要让整数变量溢出，把它们转成无符号整数：反正这个转换是免费的。

### 整数类型 {#integer-types}

整数有各种尺寸，但功能都大体相同。

| 位 | 字节 | 有符号 C 类型          | 无符号 C 类型         | 汇编      |
|-----:|-------|----------------------|----------------------|----------|
|    8 | 1     | `signed char`[^char] | `unsigned char`      | `byte`   |
|   16 | 2     | `short`              | `unsigned short`     | `word`   |
|   32 | 4     | `int`                | `unsigned int`       | `dword`  |
|   64 | 8     | `long long`          | `unsigned long long` | `qword`  |

[^char]: 注意 `char`、`unsigned char` 和 `signed char` 在技术上是三个不同的类型。C 标准把普通 `char` 是有符号还是无符号留给实现决定（在大多数编译器上它是有符号的）。

整数的各个位就是简单地顺序存储。唯一含糊之处是按什么顺序存——从左到右还是从右到左——这称为*字节序*（endianness）。依体系结构不同，格式可以是：

- *小端序*（little-endian）：先存*较低*位。例如 $42_{10}$ 会存成 $010101$。
- *大端序*（big-endian）：先存*较高*位。本文此前所有例子都遵循它。

这看起来像一个重要的体系结构问题，但在大多数情况下无关紧要：选定一种风格然后坚持用就行。但有些情况下确实有影响：

- 小端序的优点是只需少加载几个字节就能把值转换成更小的类型（比如 `long long` 转 `int`），多数情况下什么都不用做——多亏*寄存器别名*（register aliasing），`eax` 引用的就是 `rax` 的前 4 个字节，转换本质上是免费的。读各种尺寸类型的值也更容易——而在大端序体系结构上，从 `long long` 数组里加载一个 `int` 需要把指针移动 2 字节。
- 大端序的优点是高位字节先被加载，理论上能让"从高到低"的例程（如比较、打印）更快。你还能只加载第一个字节就完成某些检查，比如判断一个数是不是负数。

大端序也更"自然"——我们纸上写二进制数就是这么写的——但更快的类型转换带来的优势盖过了它。因此大多数硬件默认使用小端序，尽管有些 CPU 是"双端序"的，可以按需配置切换模式。

### 128 位整数 {#128-bit-integers}

有时我们需要把两个 64 位整数相乘得到一个 128 位整数——通常是作为临时值，马上就对 64 位整数取模还原。

没有 128 位寄存器来装这种乘法的结果，所以 `mul` 指令除了常规的 `mul r r` 形式（乘寄存器中的值并保留结果的低半部分）之外，还有另一种 `mul r` 模式：把 `rax` 寄存器中存的值与其操作数相乘，把结果写进两个寄存器——结果的低 64 位进 `rax`，高 64 位进 `rdx`：

```nasm
; input: 64-bit integers a and b, stored in rsi and rdi
; output: 128-bit product a * b, stored in rax (lower 64-bit) and rdx (higher 64-bit)
mov     rax, rdi
mov     r8, rdx
imul    rsi
```

一些编译器有支持这种运算的单独类型。在 GCC 和 Clang 中它以 `__int128` 的形式提供：

```cpp
void prod(int64_t a, int64_t b, __int128 *c) {
    *c = a * (__int128) b;
}
```

它的典型用例是立刻取出乘法的低半部分或高半部分然后撒手不管：

```c++
__int128_t x = 1;
int64_t hi = x >> 64;
int64_t lo = (int64_t) x; // will be just truncated
```

除乘法外的所有用途中，128 位整数就是捆绑成两个寄存器。这让一个全功能的 128 位类型显得太古怪，所以除基本算术运算外，对它的支持是有限的。例如：

```c++
__int128_t add(__int128_t a, __int128_t b) {
    return a + b;
}
```

编译为：

```nasm
add:
    mov rax, rdi
    add rax, rdx    ; this sets the carry flag in case of an overflow
    adc rsi, rcx    ; +1 if the carry flag is set
    mov rdx, rsi
    ret
```

其他平台为处理超字长乘法提供了类似机制。例如 Arm 有 `mulhi` 和 `mullo` 指令，分别返回乘法的低半部分和高半部分；x86 的 [SIMD 扩展](/hpc/simd)也有类似的 32 位指令。
