CPU 遇到条件跳转或[任何其他类型的分支](/hpc/architecture/indirect)时，并不会干等到条件算出来——而是立刻开始*推测执行*（speculative execution）看起来更可能被走的那条分支。执行期间，CPU 会为每条指令的分支走向统计信息，一段时间后，便能通过识别常见模式来预测它们。

因此，分支真正的"代价"很大程度上取决于 CPU 能把它预测得多好。如果它是纯粹的五五开掷硬币，你就得承受[控制冒险](../hazards)，丢弃整条流水线，再花 15-20 个周期把它重新填满。而如果分支永远走或永远不走，除了检查条件本身，你几乎不用付出任何代价。

## 一个实验 {#an-experiment}

作为案例，我们先创建一个数组，元素是 0 到 99（含两端）之间的随机整数：

```c++
for (int i = 0; i < N; i++)
    a[i] = rand() % 100;
```

然后写一个循环，把其中小于 50 的元素全部加起来：

```c++
volatile int s;

for (int i = 0; i < N; i++)
    if (a[i] < 50)
        s += a[i];
```

我们设 $N = 10^6$，并把循环反复跑上许多遍，以免[缓存冷启动](/hpc/cpu-cache/bandwidth)效应搅乱结果。我们把累加变量标记为 `volatile`，这样编译器就不会向量化这个循环、交错它的各次迭代，或以任何其他方式"作弊"。

在 Clang 上，它生成的汇编长这样：

```nasm
    mov  rcx, -4000000
    jmp  body
counter:
    add  rcx, 4
    jz   finished   ; "jump if rcx became zero"
body:
    mov  edx, dword ptr [rcx + a + 4000000]
    cmp  edx, 49
    jg   counter
    add  dword ptr [rsp + 12], edx
    jmp  counter
```

我们的目标是模拟一条完全不可预测的分支，而且成功做到了：这段代码每个元素耗时约 14 个 CPU 周期。要对"理论值"做个非常粗略的估计，可以假设分支在 `<` 和 `>=` 之间交替，流水线每隔一次迭代就预测失败一次。那么，每两次迭代：

- 我们丢弃一次流水线，它在 Zen 2 上有 19 个周期深（即它有 19 级，每级花一个周期）。
- 需要一次内存读取和一次比较，耗时约 5 个周期。偶数和奇数迭代的条件可以并发检查，所以姑且假设每 2 次迭代只付一次。
- 走 `<` 分支时，还需要约 4 个周期，把 `a[i]` 加到 `volatile`（存储于内存的）变量 `s` 上。

因此平均下来，每个元素需要花 $(4 + 5 + 19) / 2 = 14$ 个周期，与实测值吻合。

### 分支预测 {#branch-prediction}

我们可以把硬编码的 `50` 换成可调参数 `P`，它实际上设定了 `<` 分支的概率：

```c++
for (int i = 0; i < N; i++)
    if (a[i] < P)
        s += a[i];
```

现在，对不同的 `P` 值做基准测试，会得到一张颇为有趣的图：

![](/en/hpc/pipelining/img/probabilities.svg)

峰值在 50-55%，符合预期：分支预测失败是这里最昂贵的东西。这张图是不对称的：只检查永远不会成立的条件（`P = 0`）只要约 1 个周期，而分支永远都走（`P = 100`）时求和约需 7 个周期。

这张图并非单峰：在 85-90% 附近还有一个局部最优点。在那里每个元素约花 6.15 个周期，比永远走分支还快大约 10-15%——考虑到要执行的加法也少了。到这个点，分支预测失败不再影响性能，因为预测失败时被丢弃的不再是整个指令缓冲区，而只是那些被推测调度的操作。本质上，10-15% 的预测失败率正是个均衡点：往流水线里看得足够远、不至于停顿，同时又能因多走更廉价的 `>=` 分支省下 10-15%。

注意，检查一个永远不会（或几乎不会）发生的条件几乎不花什么钱。这正是程序员如此慷慨地使用运行时异常和基本情况检查的原因：只要它们确实罕见，就几乎不产生任何开销。

### 模式识别 {#pattern-detection}

在我们的例子中，高效分支预测所需要的不过是一个硬件统计计数器。如果历史上分支 A 走得比分支 B 多，那么推测执行分支 A 就是合理的选择。但现代 CPU 的分支预测器远比这先进，能识别复杂得多的模式。

我们把 `P` 固定回 50，然后在主求和循环之前先给数组排个序：

```c++
for (int i = 0; i < N; i++)
    a[i] = rand() % 100;

std::sort(a, a + n);
```

处理的还是同一批元素，只是顺序不同，耗时从 14 个周期降到了略多于 4 个——恰好是纯 `<` 分支与纯 `>=` 分支开销的平均值。

分支预测器能学会的模式远比"一直向左，然后一直向右"或"左右左右"复杂。只要把数组大小 $N$ 减到 1000（不排序），分支预测器就能把整条比较序列背下来，基准测试又回到了 4 个周期左右——实际上比有序数组的情况还要略快一点，因为有序情况下分支预测器需要花些时间在"永远走"和"永远不走"两个状态之间来回切换。

### 提示分支的倾向性 {#hinting-likeliness-of-branches}

如果你事先知道哪个分支更可能被走，把这些信息[告诉](/hpc/compilation/situational)编译器可能是有益的：

```c++
for (int i = 0; i < N; i++)
    if (a[i] < P) [[likely]]
        s += a[i];
```

当 `P = 75` 时，测得每元素约 7.3 个周期，而不加提示的原版需要约 8.3 个。

这个提示并不会消除分支，也不会向分支预测器传达任何信息，但它会改变[机器码布局](/hpc/architecture/layout)，让 CPU 前端处理更可能走的那个分支时略快一点（尽管通常不超过一个周期）。

这项优化只在编译期之前就能确定哪个分支更可能被走时才有收益。当分支根本无法预测时，我们可以尝试用*谓词化*（predication）把它彻底消掉——这是一个极其重要的技巧，我们将在[下一节](../branchless)中探讨。
