从缓存层级的某一层开始，缓存会在不同核心之间*共享*。这减少了总芯片面积，让你能在单块芯片上塞进更多核心，但也带来一些"吵闹邻居"问题，因为它限制了单个执行线程可用的有效缓存大小和带宽。

在大多数 CPU 上，只有最后一层缓存是共享的，而且不总是均匀共享。在我的机器上，有 8 个物理核心，L3 缓存大小为 8M，但它被分成两半：两个 4 核心组各自访问属于自己的 4M L3 缓存区域，而不是全部 8M。

还有更复杂的拓扑，其中访问内存的某些区域耗时非常量、且因核心而异（这[有时并非有意为之](https://randomascii.wordpress.com/2022/01/12/5-5-mm-in-1-25-nanoseconds/)）。这种架构特性称为*非统一内存访问*（non-uniform memory access，NUMA），安装了多颗独立 CPU 芯片的多路系统就是这种情形。

在 Linux 上，可以用 `lstopo` 获取内存系统的拓扑：

![lstopo 生成的我这颗 Ryzen 7 4700U 的缓存层级](/en/hpc/cpu-cache/img/lstopo.png)

这对并行算法有一些重要影响：多线程内存访问的性能取决于哪些核心在运行哪些执行线程。为了演示这一点，我们将并行地运行[带宽基准测试](../bandwidth)。

### CPU 亲和性 {#cpu-affinity}

与其修改源代码让它跑多线程，我们可以简单地用 [GNU parallel](https://www.gnu.org/software/parallel/) 运行多个相同的进程。为了控制哪些核心执行它们，我们用 `taskset` 设置它们的*处理器亲和性*（processor affinity）。这条组合命令运行 4 个进程，它们可以在 CPU 的前 4 个核心上运行：

```bash
parallel taskset -c 0,1,2,3 ./run ::: {0..3}
```

改变同时运行的进程数，得到如下结果：

![](/en/hpc/cpu-cache/img/parallel.svg)

现在可以看到，当数组超出 L2 缓存（每核心私有）后，进程数越多性能越差，因为各核心开始争抢共享的 L3 缓存和 RAM。

我们特意让所有进程都跑在前 4 个核心上，因为它们共享同一个统一的 L3 缓存。如果有些进程被调度到另一半核心上，L3 缓存的争用就会少一些。操作系统并不[监测](/hpc/profiling/events)这类活动——进程做什么是它自己的私事——所以默认情况下，操作系统在执行期间随意地把线程指派到核心上，不关心缓存亲和性，只考虑核心负载。

再跑一个基准测试，不过这次把进程钉在两个不同的 4 核心组上，让它们不共享 L3 缓存：

```bash
parallel taskset -c 0,1 ./run ::: {0..1}  # L3 cache sharing
parallel taskset -c 0,4 ./run ::: {0..1}  # no L3 cache sharing
```

它表现得更好——就好像可用的 L3 缓存和 RAM 带宽多了一倍：

![](/en/hpc/cpu-cache/img/affinity.svg)

这些问题在基准测试中尤其棘手，是给并行应用计时时的一个巨大噪声源。

### 饱和带宽 {#saturating-bandwidth}

看第一张图的 RAM 段，似乎核心越多，单进程吞吐量按 ½、⅓、¼ 递减，而总带宽保持不变。但这并不完全对：争用确实有害，但单个 CPU 核心通常无法占满全部 RAM 带宽。

如果把图画得更仔细，会发现总带宽其实随核心数增加而增长——尽管不成比例，并最终趋近于 ~42.4 GB/s 的理论上限：

![](/en/hpc/cpu-cache/img/parallel-bandwidth.svg)

注意我们仍然指定了处理器亲和性：$k$ 线程的运行使用前 $k$ 个核心。这就是为什么从 4 核换到 5 核时有那么大的性能提升：请求若走不同的 L3 缓存，就能获得更多的 RAM 带宽。

一般来说，要想达到最大带宽，应当始终把应用的线程对称地分开。
