把需要同时取回的数据聚在一起通常是有益的：最好放在同一条缓存行上，做不到的话，也要放在相邻的缓存行上。这能改善内存访问的[空间局部性](/hpc/external-memory/locality)，对访存受限算法的性能有正面影响。

为了演示这样做的潜在效果，我们修改[指针追逐](../latency)基准测试，让下一个指针不再由一个字段、而是由数目可变的若干个字段（$D$ 个）计算得出。

### 实验 {#experiment}

第一种做法把这些字段放在一起，作为二维数组的行。我们把这个变体称为*结构体数组*（array of structures，AoS）：

```c++
const int M = N / D; // # of memory accesses
int p[M], q[M][D];

iota(p, p + M, 0);
random_shuffle(p, p + M);

int k = p[M - 1];

for (int i = 0; i < M; i++)
    q[k][0] = p[i];

    for (int j = 1; j < D; j++)
        q[i][0] ^= (q[j][i] = rand());

    k = q[k][0];
}

for (int i = 0; i < M; i++) {
    int x = 0;
    for (int j = 0; j < D; j++)
        x ^= q[k][j];
    k = x;
}
```

在第二种做法中，我们把它们分开存放。最偷懒的办法是转置二维数组 `q`，并交换其后续所有访问中的下标顺序：

```c++
int q[D][M];
//    ^--^
```

照此类推，我们称这个变体为*数组结构体*（structure of arrays，SoA）。显然，对较大的 $D$，它的表现差得多：

![](/en/hpc/cpu-cache/img/aos-soa.svg)

两个变体的性能都随 $D$ 线性增长，但 AoS 因为数据顺序存放，需要取回的缓存行总数最多少 16 倍。即使 $D=64$，处理其余 63 个值多花的时间也小于第一次取数的延迟。

你还能看到 2 的幂处的尖峰。AoS 表现略好，因为它能用 SIMD 更快地计算[水平异或和](/hpc/simd/reduction)。相比之下，SoA 表现要差得多，但这与 $D$ 无关，而是因为 $\lfloor N / D \rfloor$（第二维的大小）是一个大的 2 的幂：这引发了一个相当复杂的[缓存相联度](../associativity)效应。

### 临时存储争用 {#temporary-storage-contention}

乍看之下似乎不该有任何缓存问题，因为 $N=2^{23}$，数组本来就大到放不进 L3 缓存。微妙之处在于：要并行处理来自不同内存位置的若干元素，你仍然需要一些空间来临时存放它们。你不能直接用寄存器，因为寄存器不够，所以它们必须存进缓存——尽管一微秒之后你就不再需要它们了。

因此，当 `N / D` 是一个大的 2 的幂、而我们沿着第一个下标迭代数组 `q[D][N / D]` 时，我们临时需要的某些内存地址会映射到同一缓存行——那里空间不够，许多元素将不得不从内存层级的上层重新取回。

这里是另一个让人挠头的问题：如果启用[大页](../paging)，不出意料，它让大多数 $D$ 值的总延迟降低了 10-15%，但对 $D=64$，它让情况糟糕了十倍：

![注意对数刻度](/en/hpc/cpu-cache/img/soa-hugepages.svg)

我怀疑连设计内存控制器的工程师都无法立刻解释清楚眼下发生了什么。

简而言之，差异源于：与每核心私有的 L1/L2 缓存不同，L3 缓存为了让共享它的不同核心之间保持一致，必须使用*物理*内存地址而不是*虚拟*地址。

当我们使用 4K 内存页时，虚拟地址在物理内存中的散布多少有些任意，这让缓存相联度问题不那么严重：物理地址将具有对 4K 字节相同的余数，而不是像虚拟地址那样对 `N / D` 取余。而当我们特意要求大页时，这个最大对齐限制提升到了 2M，缓存行受到的争用就大得多了。

这是我知道的唯一一个启用大页反而让性能变差的例子，更别说是差十倍。

### 填充的 AoS {#padded-aos}

只要我们取回的缓存行数量相同，它们位于哪里就无关紧要，对吧？来验证一下：在 AoS 代码中改用[填充的整数](../cache-lines)：

```c++
struct padded_int {
    int val;
    int padding[15];
};

const int M = N / D / 16;
padded_int q[M][D];
```

除此之外，我们仍在计算 $D$ 个填充整数的异或和。我们恰好取回 $D$ 条缓存行，但这次是顺序取回。运行时间应该与 SoA 没有差别，但实际并非如此：

![](/en/hpc/cpu-cache/img/aos-soa-padded.svg)

$D=63$ 时运行时间大约低 ⅓，但这只适用于超出 L3 缓存的数组。如果固定 $D$ 而改变 $N$，可以看到填充版本在较小的数组上表现略差，因为随机[缓存共享](../cache-lines)的机会更少了：

![](/en/hpc/cpu-cache/img/aos-soa-padded-n.svg)

由于较小数组上的性能不受影响，这显然与 RAM 的工作方式有关。

### RAM 特有的时序 {#ram-specific-timings}

从性能分析的角度看，RAM 中的所有数据物理上都存放在一个由微小电容单元组成的二维阵列中，它被划分成行和列。要读或写任何单元，你需要执行一到三个动作：

1. 把一行的内容读进*行缓冲区*（row buffer），这会暂时放掉电容上的电荷。
2. 在这个缓冲区中读或写某个具体单元。
3. 把行缓冲区的内容写回电容，以保存数据，并让行缓冲区可以服务其他内存访问。

关键就在这里：对应同一行的两次内存访问之间，你不必执行第 1 步和第 3 步——直接把行缓冲区当临时缓存用就行。这三个动作耗时大致相同，所以这个优化让长序列的行内访问比分散的访问模式快大约三倍。

![](/en/hpc/cpu-cache/img/ram.png)

行的大小因硬件而异，但通常在 1024 到 8192 字节之间。所以，尽管填充的 AoS 基准测试把每个元素放在单独的缓存行里，它们仍然非常可能位于同一 RAM 行上，整个读取序列的耗时约为原来的 ⅓，再加上第一次内存访问的延迟。
