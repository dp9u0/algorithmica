在 CPU 寄存器与 RAM 之间的数据通路上，存在一个*缓存*（cache）层级，用于加速对频繁使用数据的访问：离处理器越近的层速度越快，但容量也越小。"快"这个词在这里对应两个密切相关但彼此独立的时序指标：

- 从发起一次读或写、到数据抵达之间的延迟（*latency*）。
- 单位时间内能处理的内存操作数（*bandwidth*）。

对许多算法来说，内存带宽是缓存系统最重要的特征。同时它也是最容易测量的，所以我们先从它开始。

实验中，我们创建一个数组并对它迭代 $K$ 次，每次给元素值自增：

```cpp
int a[N];

for (int t = 0; t < K; t++)
    for (int i = 0; i < N; i++)
        a[i]++;
```

改变 $N$ 并相应调整 $K$，使访问的数组单元总数大致不变，再把总时间表示成"每秒操作数"，就得到这样一张图：

![竖直虚线是各层缓存的大小](/en/hpc/cpu-cache/img/inc.svg)

从这张图上可以清楚地看到缓存的大小：

- 当整个数组放得进最低一层缓存时，程序的瓶颈在 CPU 而不是 L1 缓存带宽。随着数组变大，与循环头几次迭代相关的开销占比变小，性能越来越接近 16 GFLOPS 的理论上限。
- 但随后性能下降：超出 L1 缓存后先降到 12-13 GFLOPS，再逐渐降到放不进 L3 缓存时的约 2 GFLOPS。

这种情况是许多轻量级循环的典型状态。

### 频率缩放 {#frequency-scaling}

CPU 缓存的各层与处理器位于同一块芯片上，因此带宽、延迟及其他所有特征都随时钟频率缩放。而 RAM 运行在自己固定的时钟上，特征保持不变。开启睿频（turbo boost）重新跑同一组基准测试，就能观察到这一点：

![](/en/hpc/cpu-cache/img/boost.svg)

在比较算法实现时，这个细节会起作用：当工作数据集放得进缓存时，两个实现的相对性能可能随 CPU 时钟频率的不同而不同，因为 RAM 不受频率影响（而其他一切都会受影响）。

因此，[建议](/hpc/profiling/noise)保持时钟频率固定；又因为睿频不够稳定，本书中的大多数基准测试都在普通的 2GHz 下运行。

### 单向访问 {#directional-access}

这个自增循环在执行期间既要做读也要做写：每次迭代中，我们取出一个值、自增、再写回。许多应用里我们只需要二者之一，所以来试试测量单向（unidirectional）带宽。

求数组之和只需要内存读：

```c++
for (int i = 0; i < N; i++)
    s += a[i];
```

而将数组清零（或填充为任何其他常量值）只需要内存写：

```c++
for (int i = 0; i < N; i++)
    a[i] = 0;
```

这两个循环都被编译器轻松[向量化](/hpc/simd)了，第二个实际上还被替换成了 `memset`，所以 CPU 在这里同样不是瓶颈（数组放得进 L1 缓存时除外）。

![](/en/hpc/cpu-cache/img/directional.svg)

单向与双向内存访问性能不同的原因，在于它们共享缓存、内存总线和其他 CPU 设施。对 RAM 而言，这造成纯读场景与读写同时进行场景之间两倍的性能差：内存控制器必须在单向内存总线上来回切换模式，带宽因此减半。L2 缓存的性能下降没那么严重：瓶颈不在缓存总线，自增循环只慢了 ~15%。

图上有一个有趣的反常之处：当数组大到触及 L3 缓存和 RAM 时，纯写循环与读写循环的性能相同。这是因为无论读还是写，CPU 在每次访问时都会把数据搬到缓存的最高层——这通常是个不错的优化，因为在许多用例中这些数据我们很快就会用到。读数据时这不是问题，因为数据本来就要途经缓存层级；但写数据时，这会导致紧随一次写之后再派发一次隐式读——也就需要两倍的总线带宽。

### 绕过缓存 {#bypassing-the-cache}

我们可以用*非临时性*（non-temporal）内存访问来阻止 CPU 预取（prefetch）我们刚写完的数据。为此，我们需要不依赖编译器向量化，更直接地重新实现清零循环。

忽略一些特殊情况，`memset` 和自动向量化的赋值循环在底层做的事情，就是用 [SIMD 指令](/hpc/simd)[搬运](/hpc/simd/moving) 32 字节的数据块：

```c++
const __m256i zeros = _mm256_set1_epi32(0);

for (int i = 0; i + 7 < N; i += 8)
    _mm256_store_si256((__m256i*) &a[i], zeros);
```

我们可以把普通的向量存储内建函数换成非临时性的版本：

```c++
const __m256i zeros = _mm256_set1_epi32(0);

for (int i = 0; i + 7 < N; i += 8)
    _mm256_stream_si256((__m256i*) &a[i], zeros);
```

非临时性读或写是在告诉 CPU：我们将来不会再用到刚访问过的这批数据，所以写完之后没必要把数据读回来。

![](/en/hpc/cpu-cache/img/non-temporal.svg)

一方面，如果数组小到放得进缓存，而我们过一小会儿确实还会访问它，这就有负面影响，因为我们将不得不完全从 RAM 读取（或者在这个场景下，我们得把它*写*进 RAM，而不是使用本地缓存的副本）。另一方面，它避免了读回，让我们更高效地使用内存总线。

事实上，RAM 场景下的性能提升超过 2 倍，甚至比纯读基准测试还快。原因是：

- 内存控制器不必在读、写模式之间来回切换总线；
- 指令序列变得更简单，允许更多挂起中的内存指令；
- 最重要的是，内存控制器对非临时性写请求可以简单地"发射后不管"——而对读请求，它必须记住数据到达后该拿它怎么办（类似网络软件中的连接句柄）。

理论上，两种请求应使用相同的带宽：读请求发送一个地址、取回数据；非临时性写请求发送地址*和*数据、什么也不取回。不论方向，传输的数据量相同，但读周期更长，因为它需要等待数据被取出。由于内存系统能处理的并发请求数[存在实际的上限](../mlp)，读写周期延迟上的这一差异也体现为它们带宽上的差异。

也是出于这些原因，单个 CPU 核心通常[无法完全占满内存带宽](../sharing)。

同样的技术可以推广到 `memcpy`：它也只是用 SIMD load/store 指令搬运 32 字节的块，同样可以改成非临时性版本，对大数组能带来两倍的吞吐量提升。还有一个非临时性加载指令（`_mm256_stream_load_si256`），用于想*读*数据又不污染缓存的场景（例如 `memcpy` 之后你不再需要原数组，但调用它之前访问过的某些数据之后还会用到）。
