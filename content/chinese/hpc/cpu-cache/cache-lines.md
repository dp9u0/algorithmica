---
title: 缓存行
weight: 3
---

CPU 缓存系统中数据传输的基本单位不是单个比特或字节，而是*缓存行（cache line）*。在大多数体系结构上，缓存行的大小是 64 字节，这意味着整个内存被划分成 64 字节的块：每当你请求（读或写）单个字节时，无论你是否需要，它所在的缓存行里其余 63 个邻居也会被一并取来。

为了演示这一点，我们给[递增循环](../bandwidth)加一个"步长"参数。现在我们只触碰每第 $D$ 个元素：

```cpp
for (int i = 0; i < N; i += D)
    a[i]++;
```

分别以 $D=1$ 和 $D=16$ 运行，可以观察到一个有趣的现象：

![纵轴按基准测试的总运行时间归一化，而非按递增的元素总数归一化](/en/hpc/cpu-cache/img/strided.svg)

随着问题规模增大，两个循环的曲线汇合到一起——尽管其中一个的工作量只有另一个的 1/16。这是因为，就缓存行而言，两个循环取回的是完全相同的内存，跨步循环只需要其中十六分之一这一点无关紧要。

当数组放进 L1 缓存时，跨步版本更快——但不是快 16 倍，而只是快 2 倍。因为它只需做一半的工作：每 16 个元素只需执行一条 `inc DWORD PTR [rdx]` 指令，而原循环处理同样的 16 个元素需要两条各 8 元素的[向量指令](/en/hpc/simd)。两个计算都受限于结果写回：Zen 2 每周期只能写一个机器字——不管这个字里装的是一个整数还是八个。

当把步长参数改为 8 时，两条曲线重合了，因为现在每 16 个元素同样需要两次递增和两次写回：

![](/en/hpc/cpu-cache/img/strided2.svg)

我们可以利用这个效应来减少[延迟基准测试](../latency)中的缓存共享，从而更精确地测量延迟。我们需要把排列的各个下标*填充（pad）*到各自独占一个缓存行：

```c++
struct padded_int {
    int val;
    int padding[15];
};

padded_int q[N / 16];

// constructing a cycle from a random permutation
// ...

for (int i = 0; i < N / 16; i++)
    k = q[k].val;
```

这样一来，当我们绕回一圈再次请求某个下标时，它被踢出缓存的概率就大得多了：

![](/en/hpc/cpu-cache/img/permutation-padded.svg)

设计和分析访存受限算法时，一个重要的实践经验是：要统计访问的缓存行数量，而不仅仅是读写操作的总次数。
