CPU 缓存系统中数据传输的基本单位不是单个的比特和字节，而是*缓存行*（cache line）。在大多数架构上，缓存行的大小是 64 字节，这意味着整个内存被划分成 64 字节的块，每当你请求（读或写）单个字节时，无论你愿不愿意，都会把同一缓存行的其余 63 个邻居一起取回来。

为了演示这一点，我们给[自增循环](../bandwidth)加一个"步长"参数。现在我们只接触每第 $D$ 个元素：

```cpp
for (int i = 0; i < N; i += D)
    a[i]++;
```

分别以 $D=1$ 和 $D=16$ 运行，可以观察到有趣的现象：

![性能按运行基准测试的总时间归一化，而不是按自增的元素总数归一化](/en/hpc/cpu-cache/img/strided.svg)

随着问题规模增长，两个循环的曲线汇合了，尽管其中一个做的工作量只有另一个的十六分之一。这是因为就以缓存行而论，两个循环取回的内存完全相同，而跨步循环只需要其中十六分之一这一事实无关紧要。

当数组放得进 L1 缓存时，跨步版本更快——虽然不是快 16 倍，而只是 2 倍。因为它只需要做一半的工作：每 16 个元素只执行一条 `inc DWORD PTR [rdx]` 指令，而原循环处理同样 16 个元素需要两条 8 元素的[向量指令](/hpc/simd)。两个计算的瓶颈都在写回结果上：Zen 2 每周期只能写一个字——不管这个字由一个整数还是八个整数组成。

把步长参数改成 8 后，两条曲线就持平了，因为现在每 16 个元素同样需要两次自增和两次写回：

![](/en/hpc/cpu-cache/img/strided2.svg)

我们可以利用这个效应来减少[延迟基准测试](../latency)中的缓存共享，把延迟测得更准。我们需要把排列的下标*填充*（padding）开，让每个下标各自占据一条缓存行：

```c++
struct padded_int {
    int val;
    int padding[15];
};

padded_int q[N / 16];

// constructing a cycle from a random permutation
// ...

for (int i = 0; i < N / 16; i++)
    k = q[k].val;
```

现在，等我们绕完一圈再次请求某个下标时，它被踢出缓存的可能性大得多：

![](/en/hpc/cpu-cache/img/permutation-padded.svg)

设计与分析访存受限算法时的重要实践教训是：数访问了多少条缓存行，而不只是内存读写总共多少次。
